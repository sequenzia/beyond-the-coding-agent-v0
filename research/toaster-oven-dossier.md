## 3. The ten documents

### D01 — Product requirements

**TO-26 · 2026-08-20 · v1 · Launch team**

**§2 Lifecycle.** The project moves through requirements, supplier tooling, engineering changes, pilot production, validation review, and the authorized launch decision. A changed heating-element configuration requires the team to review affected validation evidence before release.

**§3 Boundary.** Requirements describe intended behavior. They do not establish that the finished product passed validation. The launch authority retains the release decision.

### D02 — Earlier supplier update

**TO-26 · 2026-09-02 · v1 · Launch team**

**§1 Status.** Tooling availability is the current launch blocker. The supplier has not yet released the production tooling for pilot use.

**§2 Follow-up.** The supplier will issue a later tooling status update. This record describes status as of September 2 and does not predict subsequent readiness.

### D03 — Later supplier update

**TO-26 · 2026-09-09 · v1 · Launch team**

**§1 Status.** Tooling is available for pilot production. The tooling delay reported on September 2 has cleared.

**§2 Scope.** This update establishes tooling availability only. It does not establish completion of product validation or approve launch.

**TO-26 · 2026-09-10 · v2 · Launch team**

**§3 Follow-up.** The pilot report must identify the revised configuration. The validation owner must supply the resulting evidence to the launch-readiness review.

**§3 Decision.** Launch approval remains with the authorized review team. The review awaits validation evidence and a resulting decision. This document does not certify readiness.

## 5. Tool and state contracts

The four display names are **list documents**, **search documents**, **read document**, **save report**. Protocol identifiers may use underscores as required by a transport. Display names remain unchanged throughout the talk.

| Tool | Model supplies | Service guarantees |
|---|---|---|
| list documents | Approved collection selector, optional cursor | Authorized IDs, versions, dates, project IDs, snapshot ID, continuation cursor. Complete enumeration only when all pages succeed. No unauthorized titles or counts. |
| search documents | Query, narrowing filters, optional cursor | Access restriction intersects filters before snippets or hits leave the service. Returns source IDs, versions, sections, dates, excerpts, snapshot ID, truncation state. Empty results do not prove absence. |
| read document | Document ID, version, optional sections | Fresh authorization and version validation, canonical passages with stable references, explicit missing/unavailable/version-conflict outcome. Unauthorized and nonexistent objects are indistinguishable to this caller. |
| save report | Draft, citation manifest, stable request key | Fixed private destination bound to authenticated identity. Source-access and lineage checks. Atomic idempotent persistence. Durable receipt only after commit. |

Identity, tenant, access policy, credentials, destination, and request-key scope come from the application. Model filters can narrow access but cannot broaden it. Reject unknown arguments. Validate tool inputs and outputs. A schema constrains shape and types, not factual truth. Prompt text and document content cannot change these contracts.

**Illustrative structured search result:** `document_id: D05`, `version: v1`, `section: §2`, `date: 2026-09-11`, `project_id: TO-26`, `snapshot_id: TO-26-2026-09-13`, `excerpt: Temperature-uniformity validation remains pending.` This is service-produced structured data, not a demonstration of model structured outputs. The application can separately request schema-constrained report fields from the model. The application records trusted source lineage from retrieved context and derived notes. It does not trust a model-supplied citation list to declare all access dependencies; report authorization covers the conservatively tracked lineage as well as cited sources.

**Working state:** original request, approved scope, snapshot manifest, visited versions/sections, evidence ledger, project coverage, open questions, remaining call/time/token budgets, checkpoint ID, draft hash, and save key/status. Store evidence and decisions, not hidden model reasoning. Treat notes and summaries as derived restricted content. Recheck permissions and source versions before resuming or reopening.

**Stops:** return a supported report when the defined scope is covered and critical claims are checked. Ask for clarification when scope is ambiguous. Stop with qualified partial findings if pages fail, evidence conflicts cannot be resolved, the user interrupts, or a budget expires. Never mark unread records as reviewed or silently broaden the collection. No numerical execution budget is prescribed by this fixture.

**Save retry:** bind the key to authenticated user, run, and draft hash. Same key and same content returns the same receipt. Same key with different content returns a conflict. After a timeout, retry with the same key and content. An unknown outcome stays “save status unknown” until the service resolves it. The app verifies report identity, hash, private access, and lineage in the receipt. Reopening is an application operation, not a fifth agent tool. Current source permissions gate the entire saved report before any title, preview, cache, or body is served. Changed permissions can block report access. Editing source documents, changing permissions, email, and public sharing are absent.
